# Setup and deployment preparation

Status: in progress. Supabase is not configured. No Render deployment or final
submission is represented by these files. Run commands from the cloned repository
root containing manage.py; the clone does not contain another app wrapper folder.

## Reproducible local startup

The README is the complete fresh-clone walkthrough for Windows PowerShell and
macOS/Linux. It installs Python dependencies, runs scripts/configure_local.py,
starts the tracked compose.yaml PostgreSQL service, applies migrations and starts
Django. A private .env and matching random database credentials are generated on
each developer's machine; subsequent runs preserve them. The script also accepts
--database-url for an existing native PostgreSQL or Supabase database.

The Docker database listens on 127.0.0.1:55432 by default and stores records in a
named volume. The app runs on the host in its virtual environment. Stopping the
service preserves its volume and the local media/ upload directory. .tools/ and
.test-artifacts/ are development verification artifacts and are not needed by a
clone. Docker volumes keep their initial database credentials; keep the matching
.env when restarting the same volume.

## PostgreSQL and Supabase

Use the README's local setup. Create a new Supabase project for this increment;
`../WeFiles/` has a different User model and migration history. Do not apply the
legacy React/Supabase SQL to these Django models. Django owns authentication and
session records in PostgreSQL; it does not use Supabase Auth's `auth.users`.

Copy the **Connect > Session pooler** PostgreSQL URL (port 5432) into `.env` as
`DATABASE_URL`, replacing the password with its URL-encoded value. Remote DB
connections require SSL. Transaction pooler port 6543 is supported with
persistent connections and server-side cursors disabled. Local PostgreSQL is
also supported. There is no automatic or explicit SQLite configuration.

Django performs authorization in its server views/services. Before exposing a
Supabase project, disable its Data API if it is not used, or remove the Django
schema from the exposed schemas and revoke `anon`/`authenticated` access to its
tables. Django's User IDs are not Supabase Auth user IDs. Browser clients must
never receive PostgreSQL passwords or S3 credentials.

## Private file storage

In Supabase Storage, create a **private** bucket named `wefiles-private` with a
50 MiB file-size limit. Keep it private; never enable public access. Open Storage
settings, enable S3 access, and generate server-side S3 credentials. Copy the
endpoint and region shown by Supabase, then set:

```dotenv
PRIVATE_STORAGE_BACKEND=supabase
SUPABASE_S3_ENDPOINT_URL=https://PROJECT_REF.storage.supabase.co/storage/v1/s3
SUPABASE_S3_REGION=YOUR_PROJECT_REGION
SUPABASE_S3_ACCESS_KEY_ID=YOUR_S3_ACCESS_KEY
SUPABASE_S3_SECRET_ACCESS_KEY=YOUR_S3_SECRET
SUPABASE_STORAGE_BUCKET=wefiles-private
```

These are S3 credentials, not an anon key or a Supabase Auth password. The
backend stores random object keys and streams downloads after ownership/role
checks. It does not generate public URLs or browser signed URLs. Credential
access is privileged, so the bucket must be private and credentials server-only.

With `DJANGO_DEBUG=True`, `PRIVATE_STORAGE_BACKEND=local` writes private bytes to
`PRIVATE_MEDIA_ROOT` (default `media/`). This directory is ignored. Local objects
are not automatically copied to Supabase; use disposable files until the bucket
is configured. `DJANGO_DEBUG=False` refuses local storage, including on Render.

## Environment

| Variable | Value/purpose |
| --- | --- |
| SECRET_KEY | Random value of at least 50 characters; generated by the Render Blueprint |
| DJANGO_DEBUG | True for local development; False for Render |
| DATABASE_URL | Generated local PostgreSQL URL, or an explicitly configured hosted URL |
| POSTGRES_DB / POSTGRES_USER / POSTGRES_PASSWORD | Local Compose database, login and generated password |
| POSTGRES_PORT | Local Compose host port, default 55432; match DATABASE_URL when changing it |
| ALLOWED_HOSTS | Explicit comma-separated hosts; Render's hostname is added automatically |
| CSRF_TRUSTED_ORIGINS | Custom HTTPS origins; Render's HTTPS origin is added automatically |
| TRUST_PROXY | True only behind the trusted Render proxy |
| PRIVATE_STORAGE_BACKEND | local in debug mode, supabase in production |
| PRIVATE_MEDIA_ROOT | Local-only private upload directory |
| SUPABASE_S3_ENDPOINT_URL | HTTPS S3 endpoint copied from Supabase |
| SUPABASE_S3_REGION | Region copied from Supabase |
| SUPABASE_S3_ACCESS_KEY_ID | Server-only S3 access key |
| SUPABASE_S3_SECRET_ACCESS_KEY | Server-only S3 secret |
| SUPABASE_STORAGE_BUCKET | Existing private bucket name |
| TEST_DATABASE_URL | Separate disposable PostgreSQL/Supabase test database |
| ALLOW_DISPOSABLE_SUPABASE_TESTS | yes only when explicitly using an empty disposable Supabase test project |

## Verification

The README lists offline checks. Run the full suite against a separate local
PostgreSQL database with a `CREATEDB` test login. Its database name/URL must differ
from `DATABASE_URL`. GitHub Actions provides a PostgreSQL service automatically.

For Supabase, create a second, disposable project, set its connection URL as
`TEST_DATABASE_URL`, set `ALLOW_DISPOSABLE_SUPABASE_TESTS=yes`, and run:

```powershell
python manage.py test --settings=config.test_settings --keepdb --parallel 1
```

This reuses and flushes that project's tables. Never point it at your app project.
Tests store temporary file bytes locally; a passing PostgreSQL suite does not
prove Supabase S3 connectivity. Perform the manual upload/download/delete
acceptance flow against the configured private bucket before release.

## Render - prepare now, deploy later

Keep the same GitHub repository, named `WeFiles-Lastname-Firstname-Section`, public
for submission. This folder is its Django app root; if it remains in a monorepo,
set Render's Root Directory to its exact folder path and adapt workflow paths.
Do not create a new remote or replace another repository's history blindly.

Once ready to deploy:

1. Complete Supabase DB/bucket setup and the feature - develop - main PR flow.
2. Create a Render web service/Blueprint from the same repository and `main`.
   `autoDeployTrigger: off` disables later automatic deploys; Blueprint creation
   still triggers its first deployment.
3. Enter `DATABASE_URL` and the five Supabase S3 settings. Keep
   `DJANGO_DEBUG=False`, `TRUST_PROXY=True`, `PRIVATE_STORAGE_BACKEND=supabase`.
4. Build: `bash build.sh`. Start: `bash start.sh`. Health check: `/health/`.
   Build installs dependencies, runs deployment checks and collects static files;
   it does not migrate a database. Start applies migrations, retries deletion
   jobs, then starts Gunicorn. Target one service instance initially; move
   migrations to a pre-deploy job before scaling to multiple instances.
5. For custom domains, set explicit `ALLOWED_HOSTS` and HTTPS
   `CSRF_TRUSTED_ORIGINS`. Check HTTP redirects to HTTPS, cookies and CSS.
6. Register isolated demo accounts and promote the admin from the server terminal.
   Complete the manual flow and verify file bytes survive a restart/redeploy.

No Render persistent disk is needed with Supabase Storage. There is no automatic
creation of cloud resources, test users or demo data. `/health/` verifies a DB
query; it does not assert bucket access or completed migrations. HTTPS, secure
cookies, nosniff, private caching and HSTS are configured. Optional subdomain
HSTS/preload remain off until domain ownership is confirmed.

Deletion queues are durable. The app retries after confirmed file deletion and
at startup; during an outage, retry later with:

```powershell
python manage.py process_storage_deletions --limit 100
```

## Manual acceptance before final submission

1. Register Member A, Member B and Admin accounts; promote Admin using the command.
   Check required fields, malformed email, duplicate email/username, short and
   mismatched passwords, login failure, logout, both dashboards and profile edits.
2. As Member A create a folder and subfolder, upload a small file, inspect it,
   download and compare its contents, rename/describe/move it, then delete it.
3. Try blank/oversized uploads, duplicate folder names, self/descendant moves,
   too-deep moves, nonempty folder deletion and missing delete confirmation.
4. As Member B verify A's records are absent; direct A detail/download/edit/delete
   URLs must return 404. Posting A's folder/owner IDs must not change ownership.
5. As Admin view and manage both members' records, keeping the original owners.
   Creating/uploading still uses Admin's own account.
6. Restart the deployed app and verify DB records and private bucket objects
   persist; sign out and confirm direct download redirects to login.
7. Check desktop/mobile layout and keyboard controls. Capture labeled screenshots
   for the report, including a validation error, without exposing credentials.
